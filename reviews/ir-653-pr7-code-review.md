# Code review of quire-exact PR #7: IR-653 kernel boundary and charge evidence

## Summary

Ticket: IR-653. PR: quire-exact#7, head `9a68b718bf76c6763513a484d01df28de6198dc6`, base `64baa41ce16c4ae9d614cb636b3ce567bfcc6c5a`. The reviewer checked both SHAs against `git ls-remote` and `gh pr view`; the merge base equals `origin/main`. Reviewer model `claude-opus-5-5`, run `ac997cf4-dcfc-46f2-abc1-97aadea812b5`. The rust-review lane is folded in. The diff changes no production code. It adds unit tests for FR-359 and FR-360, three integration test files for FR-361, FR-362 and FR-363, and an `allocation-counter = "0.8.1"` dev-dependency.

The reviewer read `allocation-counter` 0.8.1's source from the cargo registry. Its counters are `thread_local!`, `measure` counts only the calling thread, and the `GlobalAlloc` impl does not override `realloc` or `alloc_zeroed`, so growth through either still reaches the counted `alloc`. `bytes_total` is therefore a sound upper bound on the largest single request, as the test module doc claims. The crate's `unsafe impl` stays outside this crate, so `unsafe_code = "forbid"` still holds. Its license (`MIT/Apache-2.0`) passes `cargo deny`.

Gates run by the reviewer on the frozen head: the focused ir653 integration tests and the five new unit tests under default features and `test-support` (all pass); `make fmt-check` (exit 0); `make lint`, covering both Clippy lanes and no-std Clippy (pass); `make deny` (advisories, bans, licenses and sources ok; its one wildcard warning is the existing `ix-trace-rs` git dev-dependency, which this PR does not touch). The full `make ci` was not run, per the brief.

## Verdict

**CONDITIONAL**: two medium and two low test-oracle findings, and no high. Every FR-359, FR-360, FR-361 and FR-363 criterion, and FR-362-AC-1/2/3/5/7/8/9, has an assertion that a wrong implementation would fail. FR-359's atomicity checks snapshot every counter, the admission count and the test-support log. FR-361 measures inside a window opened after operand construction, with a ceiling stricter than the spec's. The rational, decimal-alignment and FR-363 amounts are independent literals that the reviewer re-derived from the FR formulas: B(10^(2^20)) = 3,483,295, and (0,5)/(0,0) gives 18/6/5. The weak spots are FR-362-AC-4, which never compares equal operands, and the integer half of FR-362-AC-6, whose fixture cannot tell the size formulas apart.

| FND-001 | medium | FR-362-AC-4's ordering test never compares equal operands. It iterates `values.windows(2)` over `samples()`. Replaying the seeded LCG gives 68 adjacent pairs, none with `a == b` and none with `a*89 == b*97`, so `<=` and `>=` on equal integers or rationals never reach `order_numbers`. The AC's "equality" half is checked only through the derived `PartialEq` (`left == right`), not the kernel ordering. A kernel that answered `LessOrEqual` as strict `Less` would pass. | tests/ir653_scalar.rs:204-233 |
| FND-002 | medium | FR-362-AC-6's integer fixture uses 5 and 7, which both have B = 3. The expected sizes (`bit_len(7) + 1`, `bit_len(5) + bit_len(7)`, ordering `3`) therefore cannot distinguish `max(B(a), B(c))` from `B(a)`, `B(c)` or a min, or `B(a) + B(c)` from `2·B(a)`. A kernel that sized integer add/subtract, multiply, operands or ordering from only one operand would pass. The rational fixtures (1/2, 2/3) do discriminate. | tests/ir653_scalar.rs:259-265 |
| FND-003 | low | FR-363-AC-4 also requires that "the scale-alignment power of ten is not materialized", but `huge_retained_scale_refuses_analytically_before_comparison` observes no allocations.
