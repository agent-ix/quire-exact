# FR-389: Carry admitted structural identities without digest constructors

## Description

When the caller supplies an admitted semantic identity, the `quire-exact` kernel SHALL carry its structural components through the matching typed identity constructor, compare them by that identity's componentwise rule, and preserve the existing value admission, equality, key ordering and refusal behavior of [FR-088](./FR-088-enum-and-unit-identity-in-the-kernel.md), [FR-089](./FR-089-kernel-refuses-a-population-pair.md), [FR-377](./FR-377-composite-canonical-key-across-declarations.md) and [FR-379](./FR-379-carry-a-union-member-and-its-positional-payload-as-a-kernel-value.md). No kernel identity constructor accepts a digest or checks an identity preimage. The caller, not the kernel, joins an identity to an admitted package, declaration, model selection or population binding.

## Inputs

- For `NodeKey`, the admitted QSpec FR-322 structural node id: non-empty owning package name, non-empty path of text or nested node-id segments, and ordinal from 0 through 9007199254740991. A text path segment may itself be empty; the path array may not.
- For `EffectiveId`, the caller-admitted QSpec FR-150 value `{owner_effective_type, original}`: the owner is `null` for an effective type or another `EffectiveId` for a member, and the original declaration key is `{package, node}`. For `UniverseId`, the `NodeId` of the least root type's declaration; for `PopulationId`, the `NodeId` of the declared `relation`/`population` node. The FR-150 object-universe value `{model_selection, root_types}` supplies context but is not a `UniverseId`. For `MemberId`, the caller-admitted owner arm `{node_id: NodeId}` or `{effective_id: EffectiveId}` and exact field identifier. The kernel does not infer these from a document, graph or digest.
- For enum and union members, the admitted declaration `NodeId` and case identifier of QSpec FR-201, with FR-141's `enum_value` node and FR-441's union member pair supplying admission evidence.
- For declared and compound units, respectively the admitted unit node id and the admitted canonical compound-unit term list described by QSpec FR-142.
- For read-only traversal and fallible structural copying, an existing `NodeKey` or `PathSegment` whose nested path segments may be arbitrarily deep. The caller owns any output buffer or traversal stack it chooses to allocate.

## Outputs

- Typed `NodeKey`, `EffectiveId`, `UniverseId`, `VariantId`, `MemberId`, `PopulationId` and `UnitId` values that retain the supplied components and remain distinct across their types and, for `UnitId`, domains.
- A typed construction refusal when the supplied components are not a structural identity of the selected kind. No partly constructed identity is returned.
- Borrowed views of a node key's package, ordinal and direct path segments, including borrowed nested node identities, without rebuilding an owned path.
- A structurally identical `NodeKey` or `PathSegment` from a fallible copy operation, or a typed allocation refusal without a partial result.

## Behavior

1. **Node key.** The public `NodeKey::new(package, path, ordinal)` constructor accepts an owned non-empty UTF-8 package string, a non-empty sequence of `PathSegment::Text(String)` or `PathSegment::Node(NodeKey)`, and a `u64` ordinal no greater than 9007199254740991. The nested-node variant owns a `NodeKey` directly; its storage may be shared with other keys without changing any structural component or comparison result. The constructor returns a typed refusal for an empty package or path or an ordinal above that bound. A negative ordinal cannot be passed through this signature; the QSpec V2 wire schema rejects it before construction. The key order is QSpec FR-322's componentwise order: package by exact UTF-8 bytes, then path element by element (text before nested node id, nested ids recursively by this same order, a proper prefix first), then ordinal. Equal components give equal keys, hashes and ordering, whether the caller supplies them independently or reads them from one admitted package. An imported node retains its own package name, not the importer's alias. The kernel does not check whether the owner or path joins a package. A node id read from an admitted package uses this same constructor, with no separate digest decoder.
2. **Model identities.** `EffectiveId` has a typed constructor accepting QSpec FR-150's exact recursive value `{owner_effective_type, original}` and preserves it for equality, hashing and componentwise order. The owner is `null` for an effective type and the owning `EffectiveId` for a member; the original key is `{package, node}`. A derivation fact's ordinal, rule, inputs or parent is not an `EffectiveId` component: changing one fact without changing the value leaves the id equal, while changing the owner or original key changes it. `UniverseId` accepts only the `NodeId` of the declaration node of the least root type of the object universe. It compares by `NodeId` order. The FR-150 `{model_selection, root_types}` object-universe value is separate context, not the `UniverseId` representation. `EffectiveId` and `UniverseId` are different types. The model stage supplies these identities; the kernel neither composes a model declaration nor computes a universe component.
3. **Member and population identities.** `MemberId` accepts exactly `{owner, member}`: the owner is either `{node_id: NodeId}` for a declaration-node member or `{effective_id: EffectiveId}` for an effective-declaration member, and `member` is the exact field identifier. The `node_id` arm orders before `effective_id`; within an arm the owner orders componentwise, followed by the member's UTF-8 bytes. `PopulationId` accepts only the `NodeId` of the `relation`/`population` declaration node. Binding, anchor, declared maximum and Direct, Pre or Post admission role are not identity components. Equal node ids produce equal `PopulationId`s across those roles; different population nodes remain distinct even when member types match. A `Value::Population` remains opaque to the kernel and is still refused by [FR-089](./FR-089-kernel-refuses-a-population-pair.md) in each role.
4. **Enum and union member identities.** `VariantId` accepts exactly `{owner: NodeId, case: identifier}` for an enum, union or model variant member. The owner is the declaration node; the case is compared byte for byte after the owner's componentwise order. The `value`/`enum_value` node of FR-141 records the enum member's admission, while FR-441 admits a union member pair; neither changes the `VariantId` members. A member of another declaration remains distinct even when its case text or rank matches. The union constructor no longer retypes a `NodeKey`'s digest bytes as a `VariantId`; `UnionMember` retains the admitted declaration and member name. A model variant case name may contain any non-empty UTF-8 string admitted by the selected model document and is never forced into the source-identifier character class. An empty member name is refused with a typed result, or is unrepresentable through a validated non-empty member-name type.
5. **Unit identities.** `UnitId::declared` carries the admitted declared unit `NodeId`. The `terms` arm carries QSpec FR-142's evaluator-owned ascending canonical term list of `{unit: NodeId, exponent: nonzero mathematical integer}` for root units. The empty list identifies the dimensionless unit. `declared` orders before `terms`; term arrays order element by element, each term by unit then exponent numerically. The caller supplies an admitted canonical term list; the kernel does not normalize or validate unit algebra. The two arms remain unequal even if their displayed components coincide, and each arm compares its own components without hashing them. The kernel does not turn a compound value identity into a checked-semantic graph node.
6. **API replacement.** The digest constructors (`from_digest`), `NodeKey::decode_admitted`, fixed digest byte accessors and digest-domain constants are not part of the structural identity API. Their removal is an API change, with no legacy alias or compatibility reader. Callers pass or borrow typed identities instead of assuming that identity values are `Copy`; clone preserves exact identity. The existing authored UTF-8 `ObjectId` stays an authored string identity.
7. **Borrowed node-path traversal.** The public `NodeKey` API SHALL expose a read-only borrowed node view with package, ordinal and a direct-path iterator. Each iterator item distinguishes an exact UTF-8 text segment from a borrowed nested node view. A nested view exposes the same package, ordinal and direct-path iterator, so a caller can traverse an arbitrarily deep structural identity with an explicit, caller-owned, fallibly reserved stack. Obtaining a view, advancing its iterator and obtaining a nested view allocate nothing, reconstruct no owned `Vec<PathSegment>` or `NodeKey`, and do not recurse in proportion to path depth. This is an observation API: it neither admits a new identity nor changes the component order, equality or refusal behavior above. The caller remains responsible for typed refusal when its own output or traversal allocation fails.
8. **Fallible structural construction and copy.** Alongside the existing `NodeKey::new` shape check, the public API SHALL provide `NodeKey::try_new` taking an already owned `String` package, owned `Vec<PathSegment>` path and `u64` ordinal. It applies the same structural shape checks as `new`, plus a distinct typed allocation refusal for each reservation it performs while building its direct path and shared node storage. The owned input boundary excludes an infallible `Into<String>` conversion inside `try_new`; a caller starting from `&str` fallibly copies the package before calling it. `NodeKey::try_clone` and `PathSegment::try_clone` retain exact structural components and return a distinct typed allocation refusal for every heap reservation they perform. If a nested `PathSegment` representation requires separate carrier allocation, that allocation is fallible too; the direct `PathSegment::Node(NodeKey)` carrier above requires none. The fallible copy operations make separately owned structural copies even when ordinary `Clone` shares storage. These operations use bounded call-stack depth independent of path nesting and leave their source unchanged on refusal. QSV's `compound_unit_id` currently clones root keys and exponents and formats exponents while encoding; this exact contract covers only the key and segment portions. QSV remains responsible for fallible exponent copy, formatting and its own output reservations.
9. **Requested allocation amount.** A structural allocation refusal SHALL carry `requested: usize`, the minimum additional payload bytes in the reservation that failed, rather than a proxy based on the enclosing identity or the allocator's chosen capacity. For `String::try_reserve_exact(n)` on a new string this is `n` bytes; for a direct-path `Vec` reservation of `additional` tokens this is `additional × size_of::<FlatSegment>()` bytes. A nested operand occupies one direct token; its already owned descendants are shared, not copied into that reservation. Any separate shared-payload or destruction-carrier allocation is measured at its own actual reservation. The same rule applies to the new path vector and each copied package or text string in `try_clone`. Byte-count overflow or a token-count overflow before reservation reports `requested = usize::MAX` as the unrepresentable request. Empty strings need no reservation. Invalid shape is checked before any reservation and retains its existing shape refusal without an allocation amount.
10. **Pure structural comparison.** Comparing two already constructed `NodeKey`s with `Ord::cmp` or `PartialOrd::partial_cmp` SHALL perform no heap allocation and use call-stack space bounded independently of nested path depth. This includes equal and differing keys, shallow and arbitrarily deep nested-node paths. Comparison retains Behavior 1's component order: package UTF-8 bytes, direct path segments in order with text before node, recursively ordered nested ids, proper path prefix before its extension, then ordinal only after equal package and path. It does not materialize an owned path, hash or digest and does not mutate either identity. Equality and hashing of those same keys remain consistent with `cmp == Equal`; the existing typed identity, value admission and key-ordering rules remain in force.

11. **Shared operand storage.** When constructing a derived `NodeKey` from an already constructed operand or using ordinary `NodeKey::clone` or `PathSegment::Node(NodeKey)::clone`, the kernel SHALL share immutable operand storage with work and additional memory bounded independently of operand depth and size. It does not copy descendant tokens or text. Independently constructed equal keys still compare and hash by all structural components; borrowed views still expose every nested component for a consumer to encode the full QSpec FR-322 wire form. Destruction, equality and hashing use call-stack space bounded independently of nested depth, including a 10,000-level operand chain. The separate fallible `try_clone` and policy-aware copy operations retain their deep-copy and actual-reservation contracts.

## Acceptance Criteria

| FR-389-AC-1 | Two `NodeKey`s built independently from equal admitted `{package, path, ordinal}` components compare equal, hash equally under one hasher and have `cmp == Equal`; changing only the package, a path segment or the ordinal makes them unequal. Keys with different packages order by package UTF-8 bytes; with one package, text segments sort before nested node ids, nested ids use the same order, proper path prefixes sort first, and the ordinal decides only after equal paths. Replacing an imported node's owning package with the importer's alias changes the key. | Test |

Reading the same id from an admitted package yields the same key and does not require a second digest-decoding API. A caller that names a foreign package or nonexistent node remains responsible for the join refusal outside the kernel. | Test |
| FR-389-AC-3 | Two `EffectiveId`s made from equal `{owner_effective_type, original}` values compare and hash equally, including a `null` owner for an effective type and a recursive owning `EffectiveId` for a member. Two `UniverseId`s made from equal least-root declaration `NodeId`s compare, hash and order equally; changing any `NodeId` component distinguishes them. Changing only a non-identity member of the FR-150 object-universe value while the least-root `NodeId` remains equal does not change the `UniverseId`. An effective id cannot substitute for a universe id. Both constructors accept structural components rather than a 32-byte digest, and the kernel recomputes no preimage. | Test |
| FR-389-AC-4 | Enum, union and model-variant `VariantId`s each carry only the admitted `{owner: NodeId, case: identifier}` pair. An empty union member name is refused or unrepresentable by the public constructor. No old digest shape is accepted through another public constructor. | Test |

The declaration-key ordering control uses `NodeKey::cmp` rather than digest bytes, and the union member control uses the declaration/member pair rather than a retyped node digest. | Test |

## Status

The structural identity behavior through AC-12 is implemented. AC-13 is pending under IR-1154: the current `NodeKey::cmp` allocates a comparison-frame vector. AC-14 is pending under QSL-381: the current flat key copies operand tokens during derived-key construction and ordinary clone. This status does not waive any acceptance criterion.

## Dependencies

- QSpec FR-322 defines the structural `node_id` shape and componentwise order; FR-141 defines enum-value node identity; FR-441 defines the union member pair; FR-142 defines the evaluator-owned compound-unit term identity.
- QSpec FR-150 owns the admitted EffectiveId and object-universe value; QSpec FR-201 owns the exact `MemberId`, `VariantId`, `UnitId`, `UniverseId` and `PopulationId` members and order, with TC-233 SI-01 through SI-06 as controls. The kernel holds these values and does not mint them.
- The behavioral constraints remain [FR-088](./FR-088-enum-and-unit-identity-in-the-kernel.md), [FR-089](./FR-089-kernel-refuses-a-population-pair.md), [FR-377](./FR-377-composite-canonical-key-across-declarations.md) and [FR-379](./FR-379-carry-a-union-member-and-its-positional-payload-as-a-kernel-value.md).
- QSV `compound_unit_id` in `quire-semantic-value/src/unit.rs` consumes structural `NodeKey`s while encoding a compound unit id. Its root-key cloning and nested-path traversal motivate this kernel API; exponent cloning, exponent formatting and output allocation remain QSV-owned.
