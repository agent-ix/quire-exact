# FR-359: Cumulative meter boundaries and request-proportional charging

## Description

When a charge would exceed a cumulative `u64` limit, the `quire-exact` meter SHALL return an `Incomplete` record for the first unavailable counter without wrapping or changing any consumed counter or admission count. The meter SHALL keep semantic-size charge traversal proportional to that charge's request count while preserving refusal order and admitted accounting. A standalone meter proof and an external consumer receipt qualify these claims as specified below.

## Behavior

`work_units` and `result_units` accumulate across admitted charges. An addition that equals its limit is admissible; an addition beyond its limit, including one whose exact amount cannot fit `u64`, is refused. A refused charge preserves the previously admitted state even when its work amount fits but its result amount does not. Semantic-size counters remain high-water values.

For each `Meter::charge`, validation and update of semantic-size requests SHALL use only traversals whose trip counts do not exceed that charge's request count. The charge path SHALL NOT traverse `LimitKind::ALL` or another collection whose length is independent of the charge's request count. A single request traversal is the intended design, but the bounded proof does not establish the number of separate request traversals. The FR-362 integer-arithmetic schedule supplies at most two requests per charge. This proof bound does not add a public request-count limit: FR-358 permits arbitrarily many repeated requests. The meter SHALL preserve field-order refusal, the first-inserted failing amount within a kind, same-kind per-admission maxima, atomicity, injection and cancellation order, `consumed()` for every kind, and the FR-358 log.

The standalone Kani obligation uses production `Meter::charge` for the exact three-charge FR-362 schedule and an independent reference model. Its symbolic operands range over all `i64` values; the charge limits, including `ResultUnits`, vary to exercise admitted and refused prefixes. Its test-only `cfg(kani)` model must not change a production path. The public `evaluate_integer_arithmetic` / `Outcome::from_stop` carrier is outside this charge-level obligation and is checked by the external receipt in AC-10. The implementation lane must record that Kani compiles this `#![no_std]` crate for the tagged harness.

The implementation lane must add `[lints.rust] unexpected_cfgs = { level = "warn", check-cfg = ['cfg(kani)'] }` or equivalent check-cfg configuration so `make lint` with `-D warnings` passes, while retaining the production feature set and the no_std build. The explicit non-CI lane command is `cargo kani --harness "$HARNESS" --unwind 3 --solver cadical`, where `HARNESS` is the symbol of the `cfg(kani)` harness tagged `Trace: FR-359-AC-9`, with a 16 GiB memory ceiling and 600-second timeout. Neither `make ci` nor current CI runs Kani; a follow-up must wire the harness into a persistent gate.

After the consumer re-locks to the reviewed kernel, the unchanged CG scalar tests in AC-10 provide the external IR-705/IR-17 receipt. A test passes when its own assertions hold: healthy proofs must be Kani `Verified`, while mutation controls must be Kani `Falsified` with their specified counterexamples. FR-371-AC-6 and TC-919 step 6 require the shared routed healthy, routed violating-bound, and TC-025 arithmetic-mutant controls; AC-10 additionally requires both attested receipt cases. A `MemoryExhausted`, timeout or compiler error is inconclusive for each test and does not satisfy either acceptance criterion. If the receipt fails after the Meter change, investigate the separate `Result`/`Outcome::from_stop` carrier before claiming acceptance.

## Notes

The log is a test-support diagnostic absent from production builds. Earlier Kani runs with log-content assertions ended in `MemoryExhausted` at the 16 GiB lane ceiling: two modeled charges ran for 64 s with a measured 15.4 GiB peak, and three modeled charges ran for 80 s with a measured 14.9 GiB peak. The measured peaks are below 16 GiB because each run was killed or stopped at the lane limit; neither run verified. Fixed-index log assertions also exhausted the lane, without a recorded peak here. With log assertions removed, one modeled charge measured 21 s / 1.0 GiB and two modeled charges measured 33 s / 1.8 GiB. A separate three-charge schedule with symbolic operands and limits, but without the independent model or log assertions, measured 13–15 s / at most 771 MiB. None of these no-log measurements is the full amended AC-9 configuration: three modeled charges plus the repeated-kind control, without log assertions. The implementation lane must measure and report that configuration; AC-9 is satisfied only by its actual verified run under the specified bounds, and `MemoryExhausted` remains unaccepted. A later measured peak below 16 GiB does not reinstate log assertions in AC-9: a stopped run below the ceiling is inconclusive under the lane ceiling and inconclusive-is-not-accepted rule. The previous log-content obligation had symbolic Kani coverage; AC-12 instead plans sampled unit tests with independent expected values for the named cases. The Kani obligation still covers high-water coalescing symbolically through `consumed()` for every kind.
