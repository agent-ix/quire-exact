# TC-931: Request-proportional meter accounting and bounded integer-arithmetic proof

## Description

Verify planned FR-359-AC-8, AC-9, AC-11 and AC-12 and record the permanently external AC-10 receipt. Kernel accounting and its Kani obligation belong to quire-exact. The five unchanged CG scalar tests are a separate consumer-owned IR-705/IR-17 acceptance receipt, not kernel test cases.

## Test Procedure

1. For AC-11, inspect production `Meter::charge` and called helpers for every semantic-size processing traversal. Record its collection and maximum trip count relative to that charge's request count; reject any `LimitKind::ALL` or independently sized traversal. A single request traversal is the intended design, but do not infer it from `--unwind 3`, which bounds each loop separately. Confirm the public `Charge` API adds no request-count ceiling. For AC-8, exercise zero, one, two, reordered and repeated same-kind requests and larger request counts. With `IntegerBits` limit 5, request 7 then 9 in that order and assert `next_charge = 7`, `limit = 5`, and unchanged state; the existing 9 then 7 test does not distinguish coalescing before refusal. With independent expected values, check every `consumed(kind)`, high-water and cumulative counters, exact first-short `ScalarLimits` field-order refusal including reversed attachment order, and refusal atomicity. Snapshot counters, admissions, log and truncation before an ordinary refusal; check a pending later injected occurrence, an injected denial and cancellation order on separate meters.
2. For AC-12, under `test-support`, implement `tc_931_admitted_log_matches_model_ordered_prefix` and `tc_931_admitted_log_matches_model_same_kind`, each tagged `Trace: FR-359-AC-12`. Compare every admitted record's point, absent-or-present semantic-size fields and per-admission maxima with an independent admission-by-admission model over the FR-362 schedule. Check log prefix order, absent third admission, reordered and repeated same-kind requests with zero and distinct amounts, and a refusal that leaves the log unchanged. Keep these sampled unit tests separate from the Kani harness. Cite the existing FR-358-AC-15 test in `tests/ir667_normalize.rs` for the 4096-record cap and admission-4097 truncation; do not duplicate that test under FR-359.
3. For AC-9, record that Kani compiles this `#![no_std]` crate for the tagged harness. Add `[lints.rust] unexpected_cfgs = { level = "warn", check-cfg = ['cfg(kani)'] }` or equivalent, and require `make lint` with `-D warnings` and the no_std build to remain green. Implement a standalone `cfg(kani)` harness tagged `Trace: FR-359-AC-9` over the full `i64` operand range. Call production `Meter::charge` directly for the exact FR-362 three-charge request schedule: operands with at most two semantic-size requests, arithmetic with one, and result-retain with none. This obligation ends at the private charge-level `Result` path; the public `evaluate_integer_arithmetic` / `Outcome::from_stop` carrier is checked by AC-10. Make charge limits symbolic, including `ResultUnits`, so `IntegerBits`, `ValueOccurrences`, `WorkUnits` and `ResultUnits` can each be first short and the third charge may be absent. Include separate repeated-kind controls with at most two size requests per charge. Compare point order, complete `Incomplete` fields including the first-inserted failing amount for same-kind duplicates, `ScalarLimits` field-order refusal, refusal atomicity, the admitted prefix, all resulting counters and `consumed(kind)` for every kind with a separately written model. Keep the model outside the production call path; unroll its ten-field comparisons and keep every harness/model loop within unwind 3 so an unwinding failure identifies a production loop. Assert termination via Kani's unwinding checks, with no unwinding-assertion failure. Do not assert diagnostic log contents in this harness; `Meter::charge`, counters and `consumed(kind)` need no `test-support` feature. Set `HARNESS` to the symbol of the tagged harness, then run `cargo kani --harness "$HARNESS" --unwind 3 --solver cadical` with a 16 GiB memory limit and 600-second timeout as an explicit non-CI lane. Current `make ci` and CI do not include Kani; record a follow-up to wire a persistent gate. Do not disable unwinding checks, assume the conclusion, narrow the stated symbolic domain, or route production through `cfg(kani)` logic.
4. For AC-9 mutation controls, introduce a temporary `LimitKind::ALL` traversal of charge accounting and require Kani to report an unwinding-assertion failure at that loop under the identical command and bounds. Separately swap first-short refusal order and require a model-equivalence assertion failure with a concrete counterexample. Restore production code after each control and record baseline and mutant results independently. For the real baseline, any `UnwindBoundExhausted`, resource exhaustion, timeout, compiler error or missing assertion fails acceptance. For the ALL-traversal mutant, the unwinding-assertion failure is the expected control verdict; `MemoryExhausted`, timeout or compiler error before that assertion is inconclusive and does not satisfy the control. For the refusal-order mutant, only the expected model assertion counterexample satisfies the control. A second request-proportional pass is not expected to exhaust `--unwind 3` and is not an unwinding control.
5. For AC-10, the consumer owner re-locks CG to the reviewed kernel and executes the five unchanged tests named in FR-359's verdict table. Record the kernel identity, exact selected tests, original input/domain bounds, oracle, completion and counterexample checks, unwind 3, Cadical, 16 GiB and 600 seconds, individual Kani verdicts and peak memory. The two attested-receipt tests and routed healthy test expect `Verified`; the TC-025 test expects its healthy sub-run `Verified` and its arithmetic mutant `Falsified`; the routed violating-bound test expects `Falsified`. This shares the routed healthy, bound-mutant and arithmetic-mutant controls with FR-371-AC-6 / TC-919 step 6 / AD-003; the two attested receipts are additional AC-10 evidence. A passing CG test means its own assertions held, including expected falsifications. Do not copy or edit CG harnesses into this repository or attach a local Trace tag to AC-10. If any test fails after the Meter change, report it and investigate the separate `Result`/`Outcome::from_stop` carrier before adding a further criterion.

## Expected Results

Charge processing has no traversal whose trip count exceeds the charge's semantic-size request count and preserves all previously observable accounting and denial behavior without a new count limit. The named AC-12 log tests match the independent model for sampled ordered records, per-admission maxima, same-kind coalescing and refusal atomicity; the existing FR-358-AC-15 test covers the 4096-entry cap. The standalone baseline Kani proof verifies under its specified ceiling for three modeled charges plus the repeated-kind control, without log assertions; the implementation lane measures and reports this exact configuration. The ALL-traversal control reports the expected unwinding-assertion failure, and the refusal-order control reports the expected model-equivalence counterexample. Baseline `UnwindBoundExhausted`, `MemoryExhausted`, timeout, compiler error, missing mutation execution or an altered harness never counts as acceptance. All five unchanged consumer tests meet the individual `Verified` or `Falsified` verdicts in FR-359's AC-10 table and are recorded as an external receipt. An inconclusive result remains unaccepted even where FR-371-AC-6 classifies it as inconclusive for its broader qualification.
